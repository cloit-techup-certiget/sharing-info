## (문제1)
Q71
A company is using Amazon Bedrock to develop an AI-powered application that uses a
foundation model (FM) that supports cross-Region inference and provisioned throughput. The
application must serve users in Europe and North America with consistently low latency. The
application must comply with data residency regulations that require European user data to
remain within Europe-based AWS Regions.
During testing, the application experiences service degradation when Regional traffic spikes
reach service quotas. The company needs a solution that maintains application resilience and
minimizes operational complexity.
Which solution will meet these requirements?

[Answer]
B. Use Amazon Bedrock cross-Region inference profiles by specifying geographical codes in
profile IDs when the application calls the InvokeModel API. Configure separate Amazon API
Gateway HTTP APIs to direct European and North American users to the appropriate Regional
endpoints.

### **1. 문제 및 정답 확인**

* **문제:** 북미와 유럽 사용자를 대상으로 짧은 지연 시간(Low latency)을 제공하는 Amazon Bedrock 기반 AI 애플리케이션을 개발 중임. **유럽 사용자의 데이터는 유럽 기반 AWS 리전 내에 유지되어야 한다**는 데이터 레지던시(Data residency) 규정을 준수해야 함. 트래픽 스파이크 시 단일 리전 한도(Quotas)에 도달해 서비스 성능이 저하되는 문제가 발생함. 데이터 법규를 지키면서 서비스 복원력을 유지하고 운영 복잡성을 최소화하는 솔루션은?
* **정답:** **B. 애플리케이션이 InvokeModel API를 호출할 때 프로파일 ID에 지리적 코드(Geographical codes)를 지정하여 Amazon Bedrock 크로스 리전 추론 프로파일(Cross-Region inference profiles)을 사용함. 유럽 및 북미 사용자를 적절한 지역 엔드포인트로 유도하도록 별도의 Amazon API Gateway HTTP API를 구성함.**

---

### **2. 문제 설명**

* **상황:** 글로벌 AI 서비스를 운영 중인데, 유럽의 강력한 개인정보보호법(GDPR 등) 때문에 "유럽 고객이 질문한 데이터는 절대 미국 서버로 넘어가면 안 된다"는 엄격한 규칙이 있습니다. 그런데 특정 리전(예: 프랑크푸르트)에 접속자가 폭주하면 서버가 한도 초과(Throttling)로 뻗어버리는 문제가 생겼습니다.
* **미션:** 유럽 데이터는 무조건 '유럽 대륙' 안에서만 놀게 하면서, 프랑크푸르트가 바쁘면 파리 리전으로, 파리가 바쁘면 아일랜드 리전으로 알아서 트래픽을 돌려주는 똑똑한 분산 시스템을 만들어야 합니다.
* **핵심:** Amazon Bedrock의 **크로스 리전 추론(Cross-Region Inference, CRI)** 기능을 사용하되, 전 세계가 아닌 **특정 대륙(지리적 코드)** 내에서만 묶어서 라우팅하도록 설정하는 것입니다.

---

### **3. 정답 해설**

* **지리적 코드가 포함된 크로스 리전 추론 (Cross-Region Inference with Geographical Codes):** Bedrock에서 모델을 호출할 때 단일 리전 코드가 아닌, `eu`(유럽)나 `us`(미국) 같은 권역 코드가 붙은 프로파일 ID(예: `eu.anthropic.claude-3-sonnet...`)를 사용합니다. 이렇게 하면 트래픽이 폭주할 때 유럽(eu) 프로파일은 파리, 프랑크푸르트, 런던 등 **유럽 권역 내의 리전들 사이에서만 트래픽을 자동 분산**합니다.
* **데이터 레지던시 완벽 준수:** 유럽 트래픽이 아무리 바빠도 미국 리전으로 넘어가지 않으므로, 데이터가 지정된 지리적 경계를 벗어나지 않게 되어 규정(Compliance)을 완벽히 지킬 수 있습니다.
* **API Gateway 분리:** 북미 사용자는 `us` 프로파일이 적용된 API로, 유럽 사용자는 `eu` 프로파일이 적용된 API로 접속하도록 API Gateway 엔드포인트를 나누어 구성하면 가장 깔끔하고 운영 오버헤드가 적은 글로벌 아키텍처가 완성됩니다.

---

### **4. 문제 출제의도 분석**

* **크로스 리전 추론(CRI)의 심화 응용:** Q50번에서 다루었던 크로스 리전 추론 기능이 단순히 가용성(트래픽 분산)만을 위한 것이 아니라, **지리적 권역(Geographical Boundary) 설정**을 통해 글로벌 데이터 주권 및 레지던시 규정까지 충족할 수 있는 강력한 기능임을 이해하는지 평가합니다.
* **글로벌 MLOps 라우팅 설계:** 북미와 유럽의 트래픽을 물리적/논리적으로 분리하여 안전하게 서빙하는 인프라(API Gateway + Bedrock CRI) 설계 능력을 검증합니다.

---

## (문제2)
Q72
An international company is building an AI assistant that uses RAG. The company wants the AI
assistant to have near real-time, low-latency performance. The AI assistant must provide service
to several geographic areas. The company's customers will use proprietary data with the AI
assistant. The proprietary data must not leave the company's immediate geographic area.
Which solution will meet these requirements?

[Answer]
B. Deploy an Amazon Bedrock model in each AWS Region the company operates in. Configure
an Amazon Bedrock cross-Region model inference profile. Configure a vector database that
uses Amazon Bedrock Knowledge Bases. Store the knowledge bases in Amazon S3 in each
Region the company operates in.

### **1. 문제 및 정답 확인**

* **문제:** 다국적 기업이 RAG(검색 증강 생성) 기반 AI 비서를 구축 중임. 거의 실시간에 가까운 저지연(Low-latency) 성능을 내야 하며, 전 세계 여러 지리적 영역에 서비스를 제공해야 함. 가장 중요한 조건으로, 고객의 독점 데이터(Proprietary data)는 **해당 데이터가 속한 지리적 영역을 절대 벗어나서는 안 됨(데이터 레지던시/주권 엄수)**. 이를 충족하는 솔루션은?
* **정답:** **B. 회사가 운영되는 각 AWS 리전에 Amazon Bedrock 모델을 배포함. Amazon Bedrock 크로스 리전 모델 추론 프로파일(Cross-Region model inference profile)을 구성함. Amazon Bedrock Knowledge Bases를 사용하는 벡터 데이터베이스를 구성함. 회사가 운영되는 각 리전의 Amazon S3에 지식 기반(Knowledge bases) 데이터를 저장함.**

---

### **2. 문제 설명**

* **상황:** 글로벌 기업의 RAG 서비스입니다. 한국 고객의 사내 기밀문서, 미국 고객의 사내 기밀문서가 하나의 서버에 섞이면 각국의 데이터 보안법에 걸리게 됩니다. "우리 나라 고객 데이터는 무조건 우리 나라(또는 지정된 권역) 서버에만 저장해라!"라는 강력한 법적 제약이 있습니다. 동시에 전 세계 어디서 접속하든 AI 답변이 번개처럼 빨리 나와야 합니다.
* **미션:** 데이터를 중앙으로 한곳에 모으지 않고 각 지역에 철저히 가둬두면서도, 고객이 AI에 질문할 때 물리적 거리로 인한 지연(렉)이 없도록 AI 두뇌와 창고를 글로벌 곳곳에 분산 배치해야 합니다.
* **핵심:** **저장소(S3)와 검색 엔진(KB)의 리전별 철저한 격리**를 통해 데이터 법규를 지키고, 각 리전별 Bedrock 배포 + 크로스 리전 추론(CRI)을 통해 속도와 안정성(고가용성)을 모두 잡는 아키텍처입니다.

---

### **3. 정답 해설**

* **각 리전별 S3 및 Knowledge Bases 저장:** 데이터가 지리적 영역을 벗어나지 않게 하는 가장 확실한 방법입니다. RAG에 사용될 원본 문서(S3)와 검색용 인덱스(Vector DB)를 글로벌 단일 저장소가 아닌, 서비스를 제공하는 각 AWS 리전(예: 서울, 도쿄, 버지니아 북부 등)에 독립적으로 구축하여 데이터를 물리적으로 격리합니다.
* **각 리전별 Amazon Bedrock 모델 배포:** 모델이 멀리 있으면 통신 지연 시간이 길어집니다(Latency 증가). 각 리전에 Bedrock을 배포하여 사용자와 가장 가까운 곳에서 즉시 응답을 생성하게 함으로써 '거의 실시간' 성능을 달성합니다.
* **크로스 리전 모델 추론 프로파일 구성:** 특정 리전에 트래픽이 폭주하여 한도에 도달할 경우 성능 저하가 발생할 수 있습니다. 이때 허용된 지리적 바운더리(예: Q71에서 다룬 권역별 코드) 내에서 트래픽을 유연하게 분산시켜주는 크로스 리전 프로파일을 결합하여, 법규를 어기지 않으면서도 안정적인 서비스를 유지합니다.

---

### **4. 문제 출제의도 분석**

* **글로벌 RAG 데이터 거버넌스:** 다국적 AI 서비스를 설계할 때 가장 까다로운 데이터 주권(Data Residency)을 지키려면, RAG 아키텍처의 핵심인 스토리지(S3)와 벡터 DB(Knowledge Base)를 어떻게 배치해야 하는지(분산 및 격리) 평가합니다.
* **성능과 규제의 균형 (Well-Architected):** 데이터를 리전에 가둬두는 통제(Security/Compliance)와, 로컬 모델 배포 및 크로스 리전 추론을 통한 성능 최적화(Performance Efficiency)를 동시에 달성하는 종합적인 설계 역량을 검증합니다.

## (문제3)
Q73
A company is building a generative AI (GenAI) application that processes financial reports and
provides summaries for analysts. The application must run two compute environments. In one
environment, AWS Lambda function must use the Python SDK to analyze reports on demand. In
the second environment, Amazon EKS containers must use the JavaScript SDK to batch process
multiple reports on a schedule. The application must maintain conversational context throughout
multi-tum interactions, use the same foundation model (FM) across environments, and ensure
consistent authentication.
Which solution will meet these requirements?

[Answer]
D. Use the Amazon Bedrock Converse API and IAM roles for authentication. Pass previous
messages in the request messages array to maintain conversational context. Use programming
language-specific SDKs to establish consistent API interfaces.


### **1. 문제 및 정답 확인**

* **문제:** 금융 보고서를 처리하고 요약하는 생성형 AI 애플리케이션을 구축 중임. 애플리케이션은 두 가지 컴퓨팅 환경을 실행해야 함: (1) AWS Lambda에서 Python SDK를 사용해 온디맨드로 보고서 분석, (2) Amazon EKS 컨테이너에서 JavaScript SDK를 사용해 일정에 따라 보고서 배치 처리. 이 두 환경에서 **멀티턴(Multi-turn) 대화 컨텍스트를 유지**하고, 동일한 FM(파운데이션 모델)을 사용하며, 일관된 인증(Authentication)을 보장하는 솔루션은?
* **정답:** **D. Amazon Bedrock Converse API와 인증용 IAM 역할을 사용함. 대화 컨텍스트를 유지하기 위해 요청의 `messages` 배열(Array)에 이전 메시지를 전달함. 일관된 API 인터페이스를 확립하기 위해 프로그래밍 언어별 SDK를 사용함.**

---

### **2. 문제 설명**

* **상황:** 회사에 AI를 부르는 두 가지 시스템이 있습니다. 하나는 파이썬(Python)으로 가볍게 그때그때 동작하는 서버(Lambda)고, 다른 하나는 자바스크립트(JS)로 무겁게 왕창 돌아가는 컨테이너 서버(EKS)입니다. 언어도 다르고 실행 방식도 다르지만, 두 시스템 모두 "AI가 방금 전 대화 내용을 기억(멀티턴)"하게 만들어야 하고 로그인(인증) 방식도 똑같이 맞춰야 합니다.
* **미션:** 환경이 달라도 AI와 대화하는 '표준 통신 규격'을 맞추고, 이전 대화 내용을 AI에게 전달하는 가장 효율적이고 보안이 철저한 방법을 찾아야 합니다.
* **핵심:** 멀티턴 대화와 다양한 모델 연동에 최적화된 통합 규격인 'Converse API'를 사용하고, 안전한 AWS 표준 인증인 'IAM 역할(Role)'을 적용하는 것입니다.

---

### **3. 정답 해설**

* **Amazon Bedrock Converse API:** 과거에 쓰던 `InvokeModel` API는 모델마다 입력 데이터 모양이 달라서 코드를 모델별로 다르게 짜야 했습니다. 하지만 최신 `Converse API`는 모델이 달라도, 언어(Python, JS SDK)가 달라도 완벽하게 동일한 표준 포맷을 제공하므로 여러 환경을 운영할 때 개발 복잡성을 크게 줄여줍니다.
* **대화 컨텍스트 유지 (`messages` 배열):** AI 모델(FM)은 기본적으로 '건망증'이 있어서 이전 대화를 기억하지 못하는 상태(Stateless)입니다. 따라서 멀티턴 대화를 이어가려면, 새 질문을 던질 때 `messages` 배열에 [사용자 질문1, AI 답변1, 사용자 질문2...] 처럼 대화 기록을 차곡차곡 담아서 한 번에 보내줘야 합니다. Converse API는 이 배열 구조를 기본 스펙으로 지원하여 멀티턴 대화 구현을 매우 쉽게 만들어줍니다.
* **IAM 역할을 통한 일관된 인증:** Lambda에는 실행 역할(Execution Role)을, EKS 컨테이너에는 서비스 계정용 IAM 역할(IRSA)을 부여할 수 있습니다. 즉, 소스 코드에 API 접근 키(Access Key)를 하드코딩할 필요 없이, AWS의 기본 권한 시스템(IAM Role)만으로 두 환경 모두 안전하고 일관되게 Bedrock에 접근할 수 있습니다.

---

### **4. 문제 출제의도 분석**

* **Converse API의 가치 이해:** 다양한 언어(Python, JS)와 컴퓨팅 환경(Lambda, EKS), 그리고 모델 교체 상황에서 파편화를 막고 표준화된 멀티턴 대화를 구현하는 핵심 API가 **Converse API**임을 묻는 문제입니다.
* **클라우드 네이티브 보안(IAM):** 하드코딩된 자격 증명(API Key 등) 대신, 컴퓨팅 환경(Lambda, EKS)에 내장된 임시 자격 증명인 IAM 역할(Role)을 사용하여 보안과 일관성을 유지하는 AWS 모범 설계 원칙을 평가합니다.

## (문제4)
Q74
A company is building a serverless application that uses AWS Lambda functions to help students
around the world summarize notes. The application uses Anthropic Claude through Amazon
Bedrock. The company observed that most of the traffic occurs during evenings in each time
zone. Users report experiencing throttling errors during peak usage times in their times zones.
The company needs to resolve the throttling issues by ensuring continuous operation of the
application. The solution must maintain application performance quality. The company needs a
solution that does not require a fixed hourly cost during low traffic periods.
Which solution will meet these requirements?


[Answer]
C. Enable invocation logging in Amazon Bedrock. Monitor key metrics such as Invocations,
InputTokenCount, OutputTokenCount, and Invocation Throttles. Distribute traffic across
cross-Region inference endpoints.


### **1. 문제 및 정답 확인**

* **문제:** 전 세계 학생들의 노트 요약을 돕기 위해 AWS Lambda와 Amazon Bedrock(Anthropic Claude)을 사용하는 서버리스 애플리케이션을 운영 중임. 각 시간대의 저녁 시간에 트래픽이 집중되며, 이 피크 시간에 사용자들은 **스로틀링(Throttling, 한도 초과) 오류**를 겪고 있음. 성능 품질을 유지하면서 스로틀링 문제를 해결하되, 트래픽이 적은 시간대에는 **고정된 시간당 비용(Fixed hourly cost)이 발생하지 않는** 솔루션은?
* **정답:** **C. Amazon Bedrock에서 호출 로깅(Invocation logging)을 활성화함. Invocations, InputTokenCount, OutputTokenCount, Invocation Throttles와 같은 주요 지표를 모니터링함. 크로스 리전 추론(Cross-Region inference) 엔드포인트 전반에 걸쳐 트래픽을 분산함.**

---

### **2. 문제 설명**

* **상황:** 글로벌 학생용 AI 요약 앱입니다. 한국 학생들은 한국 시간 저녁에, 미국 학생들은 미국 시간 저녁에 접속이 폭주합니다. 이 피크 시간마다 Bedrock 서버에 요청이 너무 많이 몰려 튕기는(스로틀링) 현상이 발생하고 있습니다.
* **미션:** 서버 용량을 아예 고정으로 크게 늘려버리면(전세 내기), 학생들이 학교에 가 있는 낮 시간에는 비싼 서버 임대료만 낭비하게 됩니다(고정 시간당 비용 발생). 낮에는 안 쓰고 밤에만 몰리는 이 트래픽을, 추가 고정비 없이 유연하게 처리할 마법이 필요합니다.
* **핵심:** 기본 **'사용한 만큼만 내는(On-Demand)'** 요금제를 유지하면서, 특정 리전에 트래픽이 꽉 차면 옆 동네 한가한 리전으로 트래픽을 자동으로 넘겨주는 **'크로스 리전 추론(Cross-Region Inference)'** 기능을 도입하는 것입니다.

---

### **3. 정답 해설**

* **크로스 리전 추론 (Cross-Region Inference):** 가장 중요한 해결책입니다. 예를 들어 도쿄 리전에 저녁 트래픽이 몰려 스로틀링(Throttling) 한도에 도달하면, 크로스 리전 프로파일이 이를 감지하고 자동으로 오하이오나 버지니아 북부 등 현재 낮 시간이어서 한가한 리전으로 트래픽을 분산시킵니다.
* **고정 시간당 비용 회피 (No Fixed Hourly Cost):** 스로틀링을 해결하는 또 다른 방법인 '프로비저닝된 처리량(Provisioned Throughput)'은 전용 차선을 돈을 주고 대여하는 방식이라 24시간 내내 고정된 시간당 비용이 발생합니다. 문제에서 이를 명시적으로 피하라고 했으므로, 온디맨드 기반의 크로스 리전 추론이 정답이 됩니다.
* **모니터링 및 로깅 활성화:** 스로틀링이 언제, 얼마나 발생하는지(Invocation Throttles)와 토큰 사용량(Token Count)을 CloudWatch 지표로 정확히 파악하여 시스템의 병목 현상을 가시화합니다.

---

### **4. 문제 출제의도 분석**

* **비용 효율적인 확장성 (Cost-effective Scaling):** 스파이크성(Spiky) 트래픽 워크로드에서, 비용이 많이 드는 프로비저닝(Provisioned) 모델 대신 크로스 리전 추론(CRI)을 활용해 온디맨드 비용 구조를 유지하면서 가용성을 확보하는 아키텍처 설계 능력을 평가합니다.
* **스로틀링 해결 패턴:** 글로벌 서비스 환경에서 시차(Time zone)를 활용해 서로 다른 리전의 잉여 자원을 동적으로 활용하는 AWS 클라우드의 글로벌 인프라 이점을 묻는 문제입니다.

## (문제5)
Q75
A company is developing a new AI-powered application that needs to integrate with various
specialized tools. These tools currently run as Model Context Protocol (MCP) servers on the local
machines of developers and do not maintain states between invocations. The company plans to
deploy each MCP server as an AWS Lambda function to support the company's production
application.
The solution must be accessible to both internal applications and authorized third-party partners.
The solution must use strict authentication and authorization controls.
Which additional steps will meet these requirements with the LEAST operational overhead?

[Answer]
D. Expose the Lambda function through Amazon API Gateway HTTP API endpoints with the
Streamable HTTP transport. Use Amazon Cognito to implement OAuth authentication. Configure
API Gateway to validate OAuth tokens.


### **1. 문제 및 정답 확인**

* **문제:** 여러 특수 도구(Tools)와 연동되는 새로운 AI 애플리케이션을 개발 중임. 이 도구들은 현재 개발자의 로컬 장비에서 **MCP(Model Context Protocol) 서버**로 실행되며, 상태를 유지하지 않음(Stateless). 회사는 프로덕션 애플리케이션을 지원하기 위해 각 MCP 서버를 **AWS Lambda 함수로 배포**할 계획임. 이 솔루션은 내부 앱과 인가된 외부 서드파티 파트너 모두가 접근할 수 있어야 하며, 엄격한 인증 및 인가(Authentication and authorization) 제어를 사용해야 함. **최소한의 운영 오버헤드**로 이를 충족하는 추가 단계는?
* **정답:** **D. Amazon API Gateway HTTP API 엔드포인트(Streamable HTTP 전송 사용)를 통해 Lambda 함수를 노출함. OAuth 인증을 구현하기 위해 Amazon Cognito를 사용함. OAuth 토큰을 검증하도록 API Gateway를 구성함.**

---

### **2. 문제 설명**

* **상황:** 개발자 PC에서만 돌아가던 AI 보조 도구(MCP 서버)를 이제 실제 서비스(Production) 환경에 올려서, 우리 회사 직원들과 외부 파트너사 모두가 안전하게 쓸 수 있게 만들려고 합니다. 서버 관리가 필요 없는 Lambda에 올리기로는 했는데, 외부에서 이 Lambda로 어떻게 접속하게 할지, 또 아무나 못 들어오게 어떻게 막을지가 고민입니다.
* **미션:** 외부에서 Lambda로 들어오는 '문(API)'을 만들고, '신분증(토큰) 검사기'를 달아야 합니다. 이때 개발자가 직접 인증 서버를 만들거나 복잡한 코드를 짜지 않고, AWS가 다 해주는(운영 오버헤드 최소화) 가장 편한 방법을 찾아야 합니다.
* **핵심:** 가볍고 빠른 API Gateway(HTTP API)와 AI 응답을 끊김 없이 실시간으로 보내주는 **스트리밍 전송(Streamable HTTP)**, 그리고 AWS의 인증 전문 서비스인 Cognito(OAuth)를 결합하는 것입니다. (참고: Q52번과 매우 유사한 아키텍처 패턴입니다.)

---

### **3. 정답 해설**

* **API Gateway HTTP API 및 Streamable HTTP:** 외부 사용자가 Lambda를 직접 호출할 수는 없으므로, 앞단에 API Gateway를 세워 문을 열어줍니다. 기존 REST API보다 가볍고 저렴한 'HTTP API'를 사용하며, 특히 AI 에이전트나 MCP 서버처럼 중간 경과나 긴 텍스트를 실시간으로 내보내야 하는 경우 스트리밍 전송(Streamable HTTP, 예: Server-Sent Events)을 사용하여 지연 시간(Latency)을 최소화합니다.
* **Amazon Cognito 및 OAuth 인증:** 내부 직원과 외부 파트너의 접근을 엄격히 통제하기 위해, 직접 인증 서버를 구축하지 않고 완전 관리형 서비스인 **Amazon Cognito**를 사용합니다. Cognito는 국제 표준 신분증인 'OAuth 2.0 토큰'을 발급해 줍니다.
* **API Gateway의 내장 토큰 검증:** Lambda 안에 인증 코드를 짜넣거나 별도의 인증용 Lambda(Custom Authorizer)를 만들 필요가 없습니다. API Gateway HTTP API에는 **'JWT 인가자(Authorizer)' 기능이 내장**되어 있어, 설정만 해두면 들어오는 토큰이 Cognito에서 발급한 진짜 토큰인지 자동으로 검사(Validate)합니다. 이 덕분에 운영 및 개발 오버헤드가 극적으로 줄어듭니다.

---

### **4. 문제 출제의도 분석**

* **MCP 및 GenAI 에이전트 네트워크 구축:** 최근 AI 생태계의 핵심인 MCP(Model Context Protocol) 서버를 AWS 클라우드 네이티브(서버리스) 환경으로 옮길 때, 실시간 양방향/스트리밍 통신을 지원하는 **Streamable HTTP**의 필요성을 인지하고 있는지 평가합니다.
* **서버리스 API 보안 (Least Operational Overhead):** 서드파티(외부 파트너) 통합 환경에서 가장 운영 부담이 적은 인증 체계는 Custom Logic이 아닌, **API Gateway의 기본 JWT 인가자 + Cognito OAuth**의 조합이라는 모범 설계 패턴을 묻는 문제입니다.

---

* [Amazon API Gateway HTTP API에 대한 JWT 인가자(Cognito 연동) 구성](https://docs.aws.amazon.com/ko_kr/apigateway/latest/developerguide/http-api-jwt-authorizer.html)

## (문제6)
Q76
A company has a generative AI (GenAI) application that uses Amazon Bedrock to provide
real-time responses to customer queries. The company has noticed intermittent failures with API
calls to foundation models (FMs) during peak traffic periods.
The company needs a solution to handle transient errors and provide detailed observability into
FM performance. The solution must prevent cascading failures during throttling events and
provide distributed tracing across service boundaries to identify latency contributors. The
solution must also enable correlation of performance issues with specific FM characteristics.
Which solution will meet these requirements?


[Answer]
B. Configure the AWS SDK with standard retry mode and exponential backoff with jitter. Use AWS
X-Ray tracing with annotations to identify and filter service components.


### **1. 문제 및 정답 확인**

* **문제:** Amazon Bedrock을 사용하는 생성형 AI 애플리케이션에 트래픽이 몰리는 피크 시간대마다 파운데이션 모델(FM) API 호출이 간헐적으로 실패함. (1) 일시적인 오류(Transient errors)를 처리하고, (2) 스로틀링 중 연쇄적인 장애(Cascading failures)를 방지하며, (3) 지연 시간의 원인을 찾기 위한 서비스 간 분산 추적(Distributed tracing)을 제공하고, (4) 특정 FM 특성과 성능 문제를 상관지어 분석(Correlation)할 수 있는 솔루션은?
* **정답:** **B. 지터(Jitter)가 포함된 지수 백오프(Exponential backoff)와 표준 재시도 모드(Standard retry mode)를 갖춘 AWS SDK를 구성함. 서비스 구성 요소를 식별하고 필터링하기 위해 주석(Annotations)이 포함된 AWS X-Ray 추적을 사용함.**

---

### **2. 문제 설명**

* **상황:** 피크 타임에 수많은 사용자가 동시에 AI에게 질문을 던지면, Bedrock 서버가 과부하를 막기 위해 일부 요청을 거절(스로틀링/에러)합니다. 이때 모든 사용자의 앱이 동시에 "다시 접속!"을 외치면 서버가 완전히 뻗어버리는 연쇄 붕괴가 일어납니다. 또한 시스템이 복잡해지면서 도대체 어느 구간(네트워크, AI 모델, 데이터베이스 등)에서 응답이 지연되는지 파악하기가 어렵습니다.
* **미션:** 서버가 거절했을 때 똑똑하게 시간 차이를 두고 재접속하게 만들고, 사용자의 클릭 한 번이 서버의 어느 구간들을 거쳐가는지 마치 엑스레이(X-Ray) 사진을 찍듯 훤히 들여다볼 수 있어야 합니다.
* **핵심:** 클라우드의 표준 장애 극복 패턴인 지수 백오프 및 지터(Jitter)로 트래픽을 분산시키고, **AWS X-Ray**를 통해 시스템 전체의 흐름을 추적하면서 '주석(Annotation)'을 달아 어떤 AI 모델에서 문제가 생겼는지 쉽게 검색하는 것입니다.

---

### **3. 정답 해설**

* **표준 재시도 및 지터가 포함된 지수 백오프 (Exponential Backoff with Jitter):** Q60번에서도 다루었던 핵심 복원력 패턴입니다. API 호출이 실패하면 즉시 재시도하지 않고 대기 시간을 기하급수적으로 늘리며(1, 2, 4, 8초...), 동시에 난수(Jitter)를 섞어 수많은 요청의 재시도 타이밍을 흩어지게 만듭니다. AWS SDK의 `Standard` 재시도 모드에는 이 기능이 기본으로 내장되어 있어 연쇄 장애를 훌륭하게 방지합니다.
* **AWS X-Ray 분산 추적 (Distributed Tracing):** MSA(마이크로서비스) 환경에서 요청이 API Gateway $\rightarrow$ Lambda $\rightarrow$ Bedrock으로 흘러가는 전 과정을 시각적으로 추적하여, 정확히 어느 구간에서 병목(Latency)이 발생했는지 찾아냅니다.
* **주석 (Annotations) 활용:** 단순한 로그(Metadata)와 달리, X-Ray의 '주석(Annotations)'은 인덱싱(Indexing)이 되어 필터링과 검색이 가능합니다. 추적 데이터에 `Model=Claude-3`, `Version=v1` 같은 주석을 달아두면, 나중에 "Claude 3 모델에서 발생한 지연 시간만 모아서 보기(Correlation)"가 가능해집니다.

---

### **4. 문제 출제의도 분석**

* **안정성 (Resiliency):** 일시적 오류(Transient Error)에 대처하기 위해 하드코딩된 재시도 로직 대신, **AWS SDK에 내장된 표준 재시도(지터 포함 백오프)** 메커니즘을 적절히 활용할 수 있는지 평가합니다.
* **관측성 및 분산 추적 (Observability):** 단순한 CloudWatch 로그를 넘어 서비스 간 경계를 허물고 추적하는 데는 **X-Ray**가 필수적이며, 특히 성능 지표를 특정 조건으로 필터링/그룹화할 때 **Annotation(주석)** 기능을 사용해야 함을 묻는 문제입니다.

## (문제8)
Q78
An insurance company uses existing Amazon SageMaker AI infrastructure to support a

The company stores customer data that is used to train the SageMaker AI model in an Amazon S3
bucket. The dataset is growing rapidly. The company wants a solution to continuously re-train

---

### **2. 문제 설명**

* **상황:** 고객의 보험료를 정확히 예측하는 AI가 있습니다. 세상이 변하고 데이터가 쌓일수록 AI도 최신 데이터로 계속 공부(재학습)를 해야 합니다. 그런데 직원이 최신 엑셀 파일(데이터)을 클라우드 창고(S3)에 올릴 때마다, 개발자가 수동으로 재학습 버튼을 누르고 새 모델을 서버에 교체해 주는 것은 너무 번거로운 일입니다.
* **미션:** "파일 업로드"라는 행동을 감지하면, 시스템이 알아서 "AI 재학습 및 서비스 교체(배포)" 스위치를 켜는 완전 자동화 공장을 만들어야 합니다.
* **핵심:** 이벤트 신호를 감지하고 전달하는 Lambda + EventBridge(신호등/우체국)와, 신호를 받자마자 AI를 훈련시키고 배포하는 SageMaker Pipelines(MLOps 자동화 공장)의 완벽한 릴레이(Event-Driven MLOps)입니다.

---

### **3. 정답 해설**

* **이벤트 감지와 전달 (Lambda + EventBridge):**
* S3에 새로운 데이터 파일이 업로드되면, 이를 감지한 AWS Lambda가 "새 데이터가 들어왔다!"라는 알림(이벤트)을 생성합니다.
* 이 알림은 AWS의 중앙 통신망인 **Amazon EventBridge**를 타고 목적지를 향해 날아갑니다. 여기서 EventBridge는 Lambda를 '출발지(Source)'로, SageMaker Pipelines를 '도착지(Target)'로 설정하여 신호를 정확하게 전달합니다.


* **SageMaker Pipelines (지속적 학습 파이프라인):** 머신러닝의 복잡한 과정(데이터 준비 $\rightarrow$ 학습 $\rightarrow$ 평가 $\rightarrow$ 배포)을 하나로 엮어놓은 자동화 워크플로입니다. EventBridge의 신호(트리거)를 받으면 사람의 개입 없이 자동으로 잠자던 파이프라인이 깨어나 최신 데이터로 모델을 재학습시키고, 똑똑해진 새 모델을 프로덕션 환경에 꽂아 넣습니다. 이를 MLOps 용어로 지속적 학습(Continuous Training, CT)이라고 합니다.

---

### **4. 문제 출제의도 분석**

* **이벤트 기반 MLOps (Event-Driven MLOps):** 머신러닝 모델을 한 번 배포하고 끝내는 것이 아니라, 새로운 데이터가 유입될 때 자동으로 파이프라인을 트리거하여 **지속적인 재학습 및 재배포(CT/CD)** 체계를 구축할 수 있는지 평가합니다.
* **아키텍처 구성 요소의 결합:** 서비스들을 서로 얽히게 만들지 않고, **Amazon EventBridge**를 중앙 이벤트 버스로 활용하여 느슨하게 결합(Loosely coupled)된 확장성 높은 워크플로를 설계하는 AWS 모범 사례를 묻는 문제입니다.

### **1. 문제 및 정답 확인**

* **문제:** 의료 정보를 사용자에게 제공하기 위해 Amazon Bedrock 기반의 RAG(검색 증강 생성) 시스템을 구현함. (1) 여러 청킹(Chunking) 전략을 비교하고, (2) 두 개의 파운데이션 모델(FM)의 생성 품질을 평가하며, (3) 배포를 위한 품질 임계값(Thresholds)을 강제해야 함. 이 요구사항을 충족하는 Bedrock 평가 구성은?
* **정답:** **B. 사용자 지정 'precision at k(k에서의 정밀도)' 지표와 1~5점 척도를 사용하는 'LLM-as-a-judge(심판으로서의 LLM)' 지표를 사용하는 '검색 및 생성(Retrieve-and-generate) 평가 작업'을 생성함. 평가 데이터셋에 각 청킹 전략을 포함함. 지원되는 버전의 Anthropic Claude Sonnet을 사용하여 두 FM의 응답을 평가함.**

---

### **2. 문제 설명**

* **상황:** 방대한 의학 백과사전으로 대답해 주는 AI(RAG)를 만들었습니다. 그런데 사전을 '한 페이지씩' 잘라서 AI에게 줄지, '한 문단씩' 잘라서 줄지(청킹 전략) 고민입니다. 또한 A 모델과 B 모델 중 누가 더 의학 설명을 잘하는지(생성 품질) 채점해서, 기준 점수(임계값)를 넘는 모델만 실제 서비스에 올리려고 합니다.
* **미션:** 검색 성능(문서를 잘 찾아왔는가?)과 대답 성능(말을 잘 만들었는가?)을 동시에, 그것도 사람이 일일이 채점하는 것이 아니라 시스템이 자동으로 공정하게 채점하는 자동화된 시험장을 만들어야 합니다.
* **핵심:** Bedrock의 'RAG 특화 평가 작업'을 만들고, 똘똘한 똑똑이 AI(Claude Sonnet)를 '채점관(LLM-as-a-judge)'으로 고용하여 두 개의 AI 모델이 낸 답안지를 1~5점으로 자동 채점하게 만드는 것입니다.

### **3. 정답 해설**

* **검색 및 생성(Retrieve-and-generate) 평가 작업:** RAG 시스템은 문서를 '검색(Retrieve)'하는 과정과 답을 '생성(Generate)'하는 두 가지 과정으로 나뉩니다. Bedrock은 이 두 가지를 한 번에 평가할 수 있는 전용 평가 기능을 제공합니다.
* **Precision at k (검색 품질 평가):** AI가 찾아온 상위 k개의 문서 조각(청크) 중에 진짜 정답이 들어있는 비율을 측정합니다. 데이터셋에 '문단 단위 청킹', '페이지 단위 청킹'을 다르게 넣어 비교하면, 어떤 청킹 전략이 더 문서를 잘 검색하게 해 주는지 수치로 알 수 있습니다.
* **LLM-as-a-judge 및 Claude Sonnet (생성 품질 평가):** 사람이 1만 개의 대답을 직접 읽고 채점할 수는 없습니다. 대신 가장 성능이 뛰어난 모델 중 하나인 'Claude Sonnet'을 심판관(Judge)으로 지정하여, 두 평가 대상 모델(FMs)이 만든 의학 답변이 얼마나 정확하고 유창한지 1~5점 척도(Scale)로 채점하게 합니다. 이 점수를 바탕으로 배포 커트라인(품질 임계값)을 설정할 수 있습니다.

---

### **4. 문제 출제의도 분석**

* **RAG 파이프라인의 분리 평가:** RAG 시스템의 성능을 최적화하기 위해, 검색 단계(Retriever - Precision@k)와 생성 단계(Generator - LLM-as-a-judge)의 평가 지표를 정확히 구분하고 결합하여 사용할 수 있는지 평가합니다.
* **Bedrock 자동 모델 평가 (Model Evaluation):** 대규모 프롬프트 엔지니어링이나 모델 변경 시, 인간의 개입(Human-in-the-loop) 없이 또 다른 고성능 LLM을 평가자로 활용하는 **'LLM-as-a-judge'** 자동화 패턴을 이해하고 있는지 검증합니다.

### **1. 문제 및 정답 확인**

* **문제:** 야생동물 보호 기관이 전 세계 동물원에서 센서, 트래커, 시청각 기록기(멀티모달 데이터)를 활용하여 동물 행동을 모니터링하고 있음. 동물 행동을 연구하기 위해 이 데이터를 처리할 수 있는 GenAI 비서를 도입하려 함. (1) 자연어 쿼리를 지원하고, (2) **추측성 행동 해석(Speculative behavioral interpretations)을 방지**하며, (3) 윤리적 연구 감사를 위한 감사 로그(Audit logs)를 유지해야 함. 이를 충족하는 솔루션은?

### **2. 문제 설명**

* **상황:** 전 세계 동물원에서 수집된 비디오, 오디오(울음소리), 센서 이동 기록 등을 AI 비서에게 "최근 호랑이의 스트레스 징후가 어때?"라고 자연어로 물어보고 싶습니다. 이때 AI가 과학적 근거 없이 "호랑이가 슬퍼서 우는 것 같습니다" 같은 소설(추측)을 쓰면 연구에 치명적입니다. 또한, 엄격한 윤리 위원회의 감사를 위해 연구원들이 AI와 어떻게 상호작용했는지 모든 기록을 장부에 남겨야 합니다.
* **미션:** 영상/소리 같은 복잡한 데이터(멀티모달)를 텍스트 기반의 검색 엔진(RAG)이 읽을 수 있게 번역해주고, AI의 '근거 없는 상상력'을 차단하는 방어막을 치며, 모든 접속 및 질문 기록을 CCTV처럼 녹화하는 시스템을 조합해야 합니다.
* **핵심:** 데이터 전처리(**Transcribe & SageMaker**) $\rightarrow$ 검색 엔진(**Bedrock RAG**) $\rightarrow$ 추측/환각 방지(**Bedrock Guardrails**) $\rightarrow$ 감사 기록(**CloudTrail**)으로 이어지는 "책임감 있는 AI(Responsible AI)" 파이프라인입니다.

### **3. 정답 해설**

* **멀티모달 데이터 전처리 (Transcribe & SageMaker Processing):** Bedrock Knowledge Base(RAG)는 텍스트를 검색하는 데 특화되어 있습니다. 따라서 오디오 녹음은 음성 인식 서비스인 **Amazon Transcribe**로 텍스트로 바꾸고, 센서나 트래커 같은 원시 데이터는 **SageMaker Processing**을 통해 데이터 전처리를 수행하여 요약 텍스트로 만든 후 RAG 지식 기반(Knowledge Base)에 밀어 넣습니다(Ingest). 이렇게 해야 자연어로 검색할 수 있습니다.
* **추측성 출력 제한 (Amazon Bedrock Guardrails):** AI 모델(FM)은 질문을 받으면 데이터를 기반으로 답을 '생성'하려고 노력하기 때문에 가끔 사실이 아닌 추측(Hallucination)을 섞어냅니다. 이를 방지하기 위해 **Bedrock Guardrails**에 정책을 설정하여 과학적 사실에만 기반하여 답변하고, 추측성 해석은 원천적으로 차단하도록 통제합니다.
* **연구 활동 감사 로깅 (AWS CloudTrail):** 윤리적 연구 및 컴플라이언스를 위해서는 누가, 언제, 어떤 데이터에 접근하여 어떤 프롬프트를 실행했는지 증명해야 합니다. AWS의 모든 API 호출 내역을 기록하는 **AWS CloudTrail**을 활성화하면 완벽한 감사(Audit) 로그를 확보할 수 있습니다.
