* 07 CloudFormation,실패 시 동작 제어: 스택 생성 실패 시 원인 파악을 위해 자동 삭제를 막는 OnFailure=DO_NOTHING 옵션의 실무 활용법을 익힘.
* 08 ACM & ALB,"보안 통신(HTTPS): SSL/TLS 인증서를 HTTPS 리스너에 적용하고, 80 포트(HTTP)를 443(HTTPS)으로 리디렉션하는 보안 표준 구성을 학습함."
* 09 AWS Organizations,SCP를 통한 가드레일: 특정 OU 내의 계정들에 대해 특정 태그가 없는 리소스 생성을 중앙에서 강제 차단하는 정책(SCP) 설계를 학습함.
* 10 SSM Distributor,패키지 자동 배포: 대규모 서버(300대 이상)에 소프트웨어를 배포할 때 Distributor와 State Manager를 조합하여 업데이트를 자동화하는 법을 익힘.

## (문제1)
A company is storing backups in an Amazon S3 bucket.
The backups must not be deleted for at least 3 months after the backups are created.
What should a CloudOps engineer do to meet this requirement?
B. Enable S3 Object Lock on a new S3 bucket in compliance mode.
Place all backups in the new S3 bucket with a retention period of 3 months.

### 1. 문제 및 정답 확인
* **문제:** Amazon S3 버킷에 백업을 저장할 때, 생성 후 최소 3개월 동안은 절대 삭제되지 않도록 보장해야 함.
* **질문:** CloudOps 엔지니어가 취해야 할 조치는?
* **정답:** B. 새 S3 버킷에 '규정 준수 모드(Compliance mode)'로 S3 Object Lock을 활성화함.
* **조치:** 이후 모든 백업을 해당 버킷에 저장하고 보존 기간을 3개월로 설정함.

### 2. 문제 설명
* **상황:** 중요한 데이터(백업)를 보관 중인데, 누군가 실수로 지우거나 해커가 삭제하는 것을 원천 차단해야 함.
* **미션:** "어떤 권한을 가진 사람이라도 정해진 기간(3개월) 동안은 절대 지울 수 없게" 빗장을 걸어야 함.
* **핵심:** S3에는 데이터를 '읽기 전용'으로 고정하여 삭제를 방지하는 **Object Lock(객체 잠금)**이라는 강력한 금고 기능이 있음.

### 3. 정답 해설
* **S3 Object Lock:** WORM(Write Once, Read Many) 모델을 구현함. 한 번 쓰면 정해진 기간 동안 수정이나 삭제가 불가능함.
* **규정 준수 모드(Compliance Mode):** 이 모드는 가장 강력함. **루트 사용자(Root User)**를 포함해 그 누구도 보존 기간이 끝나기 전까지는 데이터를 삭제하거나 설정을 변경할 수 없음.
* **거버넌스 모드(Governance Mode)와의 차이:** 거버넌스 모드는 특수 권한이 있으면 삭제가 가능하지만, 문제에서 요구하는 "절대 삭제 불가" 조건을 완벽히 충족하려면 규정 준수 모드가 정답임.

### 4. 출제 의도 분석
* **데이터 무결성 및 보호 이해:** 금융이나 공공 기관처럼 법적/규제적 이유로 데이터 삭제를 엄격히 금지해야 하는 시나리오를 해결할 수 있는지 확인함.
* **S3 보안 기능 차이점 파악:** 단순한 권한 관리(IAM)나 버전 관리를 넘어, 물리적으로 삭제가 불가능하도록 설정하는 'Object Lock'의 세부 모드 차이를 아는지 평가함.

### 5. 관련 링크
* [Object Lock으로 객체 잠금](https://docs.aws.amazon.com/ko_kr/AmazonS3/latest/userguide/object-lock.html)

## (문제2)
An environment consists of 100 Amazon EC2 Windows instances.
The Amazon CloudWatch agent is deployed and running on all EC2 instances with a baseline configuration file to capture log files.
There is a new requirement to capture the DHCP log files that exist on 50 of the instances.
What is the MOST operationally efficient way to meet this new requirement?
A. Create an additional CloudWatch agent configuration filo to capture the DHCP logs.
Use the AWS Systems Manager Run Command to restart the CloudWatch agent on each EC2 instance with the append-config option to apply the additional configuration file.

### 1. 문제 및 정답 확인
* **문제:** 100대의 EC2 Windows 인스턴스 중 50대에만 DHCP 로그를 추가로 수집해야 할 때, 가장 운영 효율적인 방법은?
* **정답:** A. 추가 구성 파일을 생성하고, AWS Systems Manager(SSM) Run Command의 append-config 옵션을 사용하여 기존 설정에 병합 적용함.

### 2. 문제 설명
* **상황:** 이미 100대의 서버가 공통 설정으로 로그를 수집 중임.
* **미션:** 그중 딱 절반(50대)에만 새로운 로그 수집 규칙을 추가해야 함.
* **핵심:** 기존에 잘 돌아가던 설정을 지우거나 전체를 새로 까는 게 아니라, 필요한 부분만 '덧붙이는(Append)' 스마트한 방법이 필요함.

### 3. 정답 해설
* **append-config 활용:** CloudWatch 에이전트는 여러 설정 파일을 합칠 수 있는 기능을 제공함.
* **작동 방식:** 기존 공통 설정은 그대로 두고, DHCP 로그용 설정만 살짝 얹는 방식임.
* **SSM Run Command:** 일일이 서버에 접속할 필요 없이, AWS 콘솔에서 버튼 클릭 몇 번으로 50대 서버에 명령을 한꺼번에 전달함.
* **운영 효율성:** 수동 작업 없이 자동화된 방식으로 대상 서버만 골라 설정을 업데이트하므로 시간과 실수를 줄임.

### 4. 출제 의도 분석
* **관리 편의성 평가:** 수백 대의 서버를 하나하나 관리하는 구식 방식이 아닌, 코드나 설정을 통한 중앙 관리(Infrastructure as Code) 개념을 아는지 확인함.
* **CloudWatch 에이전트 심화 활용:** 에이전트 재시작 시 기존 설정을 덮어쓰지 않고 확장하는 append-config 옵션의 실무 지식을 평가함.
* **SSM 서비스 이해:** 대규모 인스턴스에 명령을 내릴 때 가장 적합한 도구가 Systems Manager임을 인지하는지 확인함.

### 5. 관련 링크
1) [CloudWatch 에이전트 구성 파일 생성 및 추가(Append)](https://docs.aws.amazon.com/ko_kr/AmazonCloudWatch/latest/monitoring/WhatIsCloudWatch.html)
2) [Systems Manager Run Command를 사용하여 에이전트 구성](https://docs.aws.amazon.com/ko_kr/AmazonCloudWatch/latest/monitoring/CloudWatch-Agent-Configuration-File-Details.html)

## (문제3)
A company's CloudOps engineer is troubleshooting communication between the components of an application.
The company configured VPC flow logs to be published to Amazon CloudWatch Logs However, there are no logs in CloudWatch Logs.
What could be blocking the VPC flow logs from being published to CloudWatch Logs?
A. The IAM policy that is attached to the IAM role for the flow log is missing the logs:CreateLogGroup permission.

### 1. 문제 및 정답 확인
* **문제:** VPC Flow Logs를 CloudWatch Logs로 게시하도록 설정했으나, 로그가 전혀 나타나지 않음.
* **질문:** 로그 게시를 차단하고 있을 가능성이 높은 원인은?
* **정답:** A. Flow Log를 위한 IAM 역할(Role)에 연결된 IAM 정책에 logs:CreateLogGroup 권한이 누락됨.

### 2. 문제 설명
* **VPC Flow Logs란:** 네트워크 통로(VPC)에서 오가는 데이터 패킷의 정보를 기록하는 'CCTV'와 같음.
* **상황:** CCTV(VPC)를 설치하고 녹화기(CloudWatch)를 연결했는데, 녹화본이 전달되지 않는 상황임.
* **핵심:** AWS의 모든 서비스 간 통신은 '권한(IAM)'이 필수임.
* **권한 부여:** VPC가 CloudWatch에 로그를 쓰려면, "로그 그룹을 만들고 데이터를 저장할 수 있는 권한"을 명시적으로 부여받아야 함.

### 3. 정답 해설
* **권한의 단계:** 로그를 기록하려면 먼저 로그가 담길 '방(Log Group)'을 만들고 그 안에 '내용(Log Stream)'을 써야 함.
* **logs:CreateLogGroup의 역할:** VPC Flow Logs 서비스가 CloudWatch Logs 내부에 새로운 로그 그룹을 생성할 수 있게 허용하는 권한임.
* **실패 원인:** 이 권한이 없으면 VPC는 로그를 보내고 싶어도 CloudWatch의 문을 열지 못해 데이터 전송에 실패하게 됨.

### 4. 출제 의도 분석
* **IAM 역할 및 정책 이해:** AWS 서비스가 다른 서비스를 호출할 때 사용하는 서비스 역할(Service Role) 개념을 정확히 이해하고 있는지 확인함.
* **트러블슈팅 역량:** 설정은 맞는데 동작하지 않을 때, 가장 먼저 확인해야 할 '권한(Permissions)' 문제를 식별할 수 있는지 평가함.
* **최소 권한 원칙:** 로그 게시를 위해 필요한 구체적인 API 액션(CreateLogGroup, CreateLogStream, PutLogEvents)들을 인지하고 있는지 확인함.

### 5. 관련 AWS 공식 링크
* [VPC Flow Logs를 CloudWatch Logs로 게시하기 위한 IAM 권한](https://docs.aws.amazon.com/ko_kr/vpc/latest/userguide/flow-logs-iam-role.html)
* [VPC Flow Logs 문제 해결 가이드](https://docs.aws.amazon.com/ko_kr/vpc/latest/userguide/flow-logs-troubleshooting.html)

## (문제4)
A company is migrating a legacy application to AWS.
The company manually installs and configures the legacy application on Amazon EC2 instances across multiple Availability Zones.
The company sets up an Application Load Balancer (ALB) for the application.
The company sets the target group routing algorithm to weighted random. The application requires session affinity.
After the company deploys the application, users report random application errors that were not present in the legacy version of the application.
The target group health checks do not show any failures. The company must resolve the application errors.
Which solution will meet this requirement?
A. Set the routing algorithm of the target group to least outstanding requests.

### 1. 문제 및 정답 확인
* **문제:** 수동으로 구성된 EC2 인스턴스들과 ALB를 사용 중임.
* **조건:** 타겟 그룹의 라우팅 알고리즘이 '가중치 기반 랜덤(Weighted random)'이며, 애플리케이션은 **세션 고정(Session affinity)**이 필요함.
* **질문:** 배포 후 간헐적인 오류가 발생할 때 해결 방법은?
* **정답:** A. 타겟 그룹의 라우팅 알고리즘을 '최소 미결 요청(Least outstanding requests)'으로 변경함.
* **참고:** 실제 환경에서는 'Sticky Sessions(세션 고정)' 활성화가 우선이지만, 제시된 보기 중 알고리즘 변경을 통해 부하 불균형을 해소하는 것이 정답으로 간주됨.

### 2. 문제 설명
* **상황:** 여러 대의 서버(EC2)가 있고, 입구(ALB)에서 손님(사용자)을 각 방으로 안내하고 있음.
* **문제점:** '가중치 기반 랜덤'은 운이 나쁘면 특정 서버에만 손님이 몰릴 수 있음.
* **결과:** 특히 세션 고정이 필요한 앱에서 특정 서버가 과부하 걸리면 연결이 끊기거나 에러가 발생함.
* **핵심:** 모든 서버가 골고루 일할 수 있도록 지능적인 배정 방식이 필요함.

### 3. 정답 해설
* **Least Outstanding Requests (LOR):** 현재 처리 중인 요청 수가 가장 적은 서버로 새 요청을 보내는 방식임.
* **오류 해결 원리:** 랜덤 방식은 서버의 실제 바쁜 정도를 고려하지 않음.
* **장점:** 반면 LOR은 각 서버의 실시간 부하를 체크하여 여유 있는 곳으로 보내므로, 특정 서버에 과부하가 걸려 발생하는 '랜덤 에러'를 방지함.
* **건강 상태와의 관계:** 서버가 아예 죽은 건 아니므로 헬스 체크는 통과하지만, 너무 바빠서 응답을 제대로 못 하는 상황을 해결하는 데 효과적임.

### 4. 출제 의도 분석
* **ALB 라우팅 알고리즘 이해:** 기본값인 라운드 로빈(Round Robin) 외에 상황에 맞는 알고리즘(LOR 등)을 선택할 수 있는지 확인함.
* **부하 불균형 식별:** 애플리케이션 자체 결함이 아닌, 네트워크 인프라 단의 부하 분산 전략 실패로 인한 오류를 찾아낼 수 있는지 평가함.
* **세션 유지 환경 특성 파악:** 세션이 유지되는 동안 특정 서버에 연결이 집중될 수 있는 위험성을 인지하고 있는지 확인함.

### 5. 관련 AWS 공식 링크
* [Application Load Balancer의 라우팅 알고리즘 설명](https://docs.aws.amazon.com/ko_kr/elasticloadbalancing/latest/application/introduction.html)
* [타겟 그룹의 세션 고정(Stickiness) 설정](https://docs.aws.amazon.com/ko_kr/elasticloadbalancing/latest/application/load-balancer-target-groups.html)

## (문제5)
A company is using an Amazon Aurora MySQL DB cluster that has point-in-time recovery, backtracking, and automatic backup enabled.
A CloudOps engineer needs to be able to roll back the DB cluster to a specific recovery point within the previous 72 hours.
Restores must be completed in the same production DB cluster.
Which solution will meet these requirements?
C. Use backtracking to rewind the existing DB cluster to the desired recovery point.

### 1. 문제 및 정답 확인
* **문제:** Amazon Aurora MySQL DB 클러스터를 이전 72시간 내의 특정 시점으로 되돌려야 함.
* **조건:** 이때 새로운 DB 클러스터를 생성하지 않고, 기존의 운영 DB 클러스터 내에서 복구를 완료해야 하는 방법은?
* **정답:** C. 백트래킹(Backtracking) 기능을 사용하여 기존 DB 클러스터를 원하는 복구 시점으로 되감기함.

### 2. 문제 설명
* **상황:** 실수로 중요한 데이터를 삭제하거나 잘못된 업데이트를 수행함.
* **전통적 방식(PITR):** 보통은 백업본을 가지고 '새로운' DB를 하나 더 만들어서 데이터를 옮겨야 함. 시간도 오래 걸리고 주소(Endpoint)도 바뀜.
* **백트래킹이란:** 마치 비디오 테이프를 되감는 것처럼, 현재 사용 중인 DB 그 자체를 과거의 특정 시간으로 슥 돌려버리는 기능임.
* **효율성:** 새 DB를 만들 필요가 없어 매우 빠름.

### 3. 정답 해설

* **Distributor:** 소프트웨어 설치 파일과 스크립트를 하나로 묶어 표준화된 환경을 구축함.
* **State Manager:** "항상 최신 상태여야 한다"는 정책을 정의하고 주기적으로 실행함.
* **태그 기반:** 특정 태그 서버만 골라 자동으로 작업하므로 관리가 매우 편리함.

### 4. 출제 의도 분석
* **수명 주기 관리:** 단순 1회성 설치가 아닌 지속적인 업데이트 프로세스 이해도를 확인함.
* **최소 운영 노력:** 정책에 따라 자동으로 수행하는 State Manager의 효율성을 인지하는지 평가함.
